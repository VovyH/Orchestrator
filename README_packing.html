一、先弄懂五个基础词（后面全靠它们）

token：模型眼里的"字"。一条 300 字的问答，分词后大约是 200–400 个 token。样本长短，说的就是 token 个数。
step（步）：模型看一小批数据 → 算误差 → 更新一次参数，这是一个 step。步越多，参数被修正的次数越多。
epoch（轮）：把全部数据完整过一遍。我们的实验都是 1 epoch——每条样本只被看一次。
batch（批）：一个 step 喂给模型的几条样本。传统做法固定 4 条一批。
padding（填空白）：GPU 要求一个 batch 里所有序列等长。4 条样本分别长 200、161、250、180 token，就得全部补齐到 250——补进去的空白位没有任何信息，但计算照样要做。
算例上面那 4 条样本：真实内容 791 token，补齐后实际计算 4×250=1000 token，20.9% 的算力花在空白上。这就是传统训练（LLaMA-Factory 默认做法，下称 LF）慢的第一个原因。

我们的数据集更放大了这个问题：82% 的样本落在 128–256 token，但随机组批时只要混进来一条 500 token 的长样本，整批 4 条都得补到 500。实测 LF 平均每步 835 个真实 token，补齐后要算约 1,100——约 30% 的计算在算空白。

二、LF 的补救方案 packing：把样本接成"长香肠"，但步数塌了

LF 有个开关叫 packing，思路是：既然空白是补出来的，那就别补——把短样本一条接一条拼起来，拼满一个固定长度 cutoff_len（比如 2048 token）为止，像接香肠。这样几乎没有空白。

但它的组步方式是：每个 step = batch_size（4）根这样的"香肠"。于是一个 step 要消化 2048 × 4 = 8,192 个 token。用我们的数据全集算一遍总账：

算例数据总共约 2,450,000 token。LF+pack 的总步数 ≈ 2,450,000 ÷ (2048 × 4) ≈ 299 步。而不开 packing 的 LF 是 2,931 步——开了 packing，步数反而掉到只剩十分之一。这就是文档里说的"步数比 batch 组数还少"：packing 把一整个 epoch 压缩成了几百个巨型 step。

步数塌缩不是免费的：

  • 参数更新次数掉一个数量级。299 次更新 vs 2,931 次，等于把"每天修正 10 次"变成"每天修正 1 次"，同样的数据学得更粗糙；
  • 每步窗口太大。8,192 token 的 step 让显存里的中间计算结果（激活值）暴涨，14B 模型在单卡上接近放不下，通常还得额外开省显存模式（梯度检查点），速度又赔回去；
  • 学习率曲线变粗。学习率随步数退火，几百步的曲线没有"精细收尾"，loss 最后一程压不下去。

三、Orchestrator 的做法：先把"谁和谁一起走"规划好

Orchestrator 的核心想法一句话：与其事后补空白，不如事先分好组——长度接近的样本一起走，拼出来的每一步刚好塞满、不留空白，且步子故意保持小。它在训练开始前做了一次全数据的"排班"，流程五步：

① 量长度训练前把 11,724 条样本全部分词，得到一张长度清单
→
② 分桶按长度排序，长度接近的进同一个"桶"
→
③ 定预算算出一步最多装多少 token
→
④ 组步每个桶按预算切成一小片一小片，每片就是一步
→
⑤ 拼张量把一片拼成一条序列，注意力各算各的

① 量长度：顺便认识"p90"

分词后我们对长度清单做统计。p90（第 90 百分位）意思是：把所有样本按长度从短到长排队，排在 90% 位置的那条的长度。我们的数据 p90 = 287 token——即"九成样本都不超过 287 个 token"。同理 p50 = 161（中位数：一半样本比它短）。

② 分桶：长度接近的才同桶

把样本按长度排序后从头到尾扫一遍，规则是：桶里最长的不能超过最短的 1.25 倍（这个 1.25 就是代码里的 bucket_ratio，意思是"长度差距不超过 25% 的才算接近"）。超了就开一个新桶。

算例某桶从一条 200 token 的样本开始：下一条 210（210 ÷ 200 = 1.05 ≤ 1.25，进桶）→ 再下一条 260（260 ÷ 200 = 1.30 > 1.25，开新桶）。本数据集最终切出 10 个桶，从"百来 token 的短问答桶"到"近千 token 的长文档桶"。

为什么要分桶？因为补空白的问题本质是"长短混批"。长度接近的样本放在一起，就算不拼接、只是并排，要补的空白也很少；长度差 5 倍的样本放一起，短的那条几乎全是空白。

③ 定预算：一步最多装多少 token

公式只有一行：预算 = min(4096, 2 × p90)。逐项拆开：

  • 2 × p90 = 2 × 287 = 574 ≈ 576 token：乘 2 是拍出来的经验值——刚好能装下"两条典型样本"，既有拼接空间，又不至于变成超长序列；
  • min(4096, …) 是封顶：就算数据全是超长样本，单个 step 也不超过 4,096 token，防止显存爆掉。

④ 组步：桶怎么切成步

对每个桶，先算两个数：块长 block = 这个桶自己的 p90（桶内九成样本不超过的长度），条数 count = 预算 ÷ 块长（向下取整）。然后桶里的样本按顺序每 count 条切一片，一片 = 一个 step。

算例短样本桶：块长 = 桶内 p90 ≈ 250，count = 576 ÷ 250 = 2 条/步；桶里 200 条 → 100 个 step，每个约 2×230 = 460 token。长样本桶：块长 ≈ 900，count = 576 ÷ 900 = 1 条/步，每条自己单独一步。结果：全数据共 4,993 步，平均每步 2.35 条样本、477.7 token——是预算 576 的 83% 满。

两个特殊情形：一组的总长超过 max_seq_len（1024）时拆成单样本各走一步；超过 2,048 的超长样本先分块（chunk，即把一条长样本切成若干段分别训练）再进桶。本数据只有 30 条超长样本，不影响大盘。

⑤ 拼张量：什么叫"varlen"

每一步的 2–3 条样本首尾相接拼成一条序列送进 GPU，但和 LF+pack 的香肠有一个关键区别：注意力各算各的。用 varlen（variable length，变长）模式时，第 2 条样本的 token 在做注意力时看不到第 1 条样本的内容——效果上等价于它们分开了各自算，只是搭了同一班车。这样注意力计算量按"每条的长度各自平方后求和"（短样本极便宜），而不是按整条拼接长度的平方（贵）。

因为整步只装了预算内的内容、又不需要补空白，"实打实算的 token = 有信息的 token"——实测浪费率 0.0000。

四、"小步快跑"到底快在哪

同样是 245 万 token、同样 1 epoch，三种走法：

方案每 step token总步数（=更新次数）每步耗时白算的空白
LF 传统（随机批 + 补空白）≈1,100（含空白）2,9311.71 s≈30%
LF + packing（接香肠）8,192≈299（推算）—≈0
orch（分桶 + 拼接）477.74,9930.44 s0%
  • 每步小 → 单步快：477 token 的短序列让计算全部落在 GPU 最舒服的区间，单步只要 0.44 秒，是传统做法的四分之一；
  • 零空白 → 不白算：省下的 30% 算力不浪费在空白上，全部花在真实内容；
  • 步数多 → 学得细：同样 1 epoch，参数被修正了 4,993 次，是传统做法的 1.7 倍、LF+pack 的 16.7 倍。这就是"小步快跑"——不靠单步吃成胖子，靠高频小幅度的修正把 loss 压下去（末值 0.075 vs 传统 0.285）。

一个术语备忘：梯度裁剪（clip = 1.0）是防止参数一步迈太猛的保险丝——若这一步的梯度（修正方向的强度）超过 1.0，就整体缩到 1.0。LF 的梯度常年 1.5–2.0，等于每一步都被保险丝削着走；orch 的梯度平均 0.81，基本不触发，每一步都按真实学习率前进。
